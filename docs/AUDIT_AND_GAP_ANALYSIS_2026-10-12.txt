and working: ESP32 -> MQTT -> PostgreSQL, a read API, an explainable

unlocks almost every other part of the roadmap.

Schema conflict (largest architectural issue):
- A 24-table UUID-based design exists in backend/app/models/*, Alembic
  revision b7c4e2a91d30, seed_data.py and tests/test_database.py.
- It was NEVER applied. Its Device model (UUID key, device_name,
  criticality, ...) is incompatible with the live devices table (integer key,
  device_id).
- seed_data.py contains SYNTHETIC data (192.168.1.x addresses, synthetic
  Nmap scan, ESP32-02 at 192.168.1.22, risk score 76).

Recommendation: keep the live schema as the source of truth; add about four
small tables only when needed (assessment runs, evidence, findings, risk
snapshots). Archive/park the unused 24-table design.

 G. IoT CONTEXT ENGINE
------------------------------------------------------------------------------

Source: risk_engine/features/iot_context.py and
        backend/app/services/risk_service.py

Factor                    How it is set                        Evidence-driven?
------------------------  -----------------------------------  ---------------
device_criticality        Fixed env RISK_DEVICE_CRITICALITY=0.3  No
network_exposure          Fixed env RISK_NETWORK_EXPOSURE=0.3    No
authentication_security   1.0 if anonymous flag true else 0.0    Only via flag
protocol_security         1.0 if TLS flag false else 0.0         Only via flag
firmware_security         Fixed env RISK_FIRMWARE_SECURITY=0.5   No
                          (higher = MORE risk; name suggests
                          the opposite)

Structural problems:
1. Context is GLOBAL: not per device and not per finding, so every finding
   always gets the same score (both findings = 67.5 HIGH). Findings are not
   linked to devices.
2. DOUBLE COUNTING: the same anonymous/TLS flags create the finding AND
   raise its context. "MQTT without TLS" is scored partly on protocol
   security being bad, which is the same fact as the finding itself.

------------------------------------------------------------------------------
 H. DYNAMIC RISK ENGINE (IoT-RISK-v1)
------------------------------------------------------------------------------

Formula:
  score = severity_value * 100 * 0.5 + context_value * 100 * 0.5
Severity map:
  INFO 0, LOW 0.25, MEDIUM 0.5, HIGH 0.75, CRITICAL 1.0
Context factor weights (validated at import by validate_weights()):
  device_criticality 0.30, network_exposure 0.20,
  authentication_security 0.20, protocol_security 0.20,
  firmware_security 0.10
Thresholds:
  < 20 LOW, < 40 MODERATE, < 60 MEDIUM, < 80 HIGH, >= 80 CRITICAL
Output:
  RiskResult with score, level, model version and per-factor contributions.

Scenarios reproduced in memory during the audit:

Scenario                                         Score   Level
-----------------------------------------------  ------  --------
A - sensor context, HIGH severity                 67.5   HIGH
B - critical context, HIGH severity               82.5   CRITICAL
HIGH severity, TLS + authentication fixed         47.5   MEDIUM
HIGH severity, TLS only fixed                     57.5   MEDIUM
LOW severity, minimum context                     12.5   LOW
CRITICAL severity, maximum context               100.0   CRITICAL
INFO severity, maximum context                    50.0   MEDIUM  <-- issue

Assessment:
- Implementation matches the specification; scores are reproducible and
  explainable.
- "Same vulnerability, different context -> different score" is
  demonstrable, but it is a mathematical property of the formula, NOT
  empirical evidence.
- Context alone can lift an INFO finding to MEDIUM; needs justification or a
  guard.
- Missing: automated tests with assertions, persistence/history,
  sensitivity analysis, rationale for the weights and the 50/50 split.
